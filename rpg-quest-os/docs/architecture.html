01全体構成

常時起動するサーバーを一切持たない。Cloudflare のエッジ上で「静的配信（Pages）」と「都度実行の API（Workers）」に分離し、 認証は Cloudflare Access に委譲する。AWS / GCP の運用対象は存在しない。

この構成を選んだ理由。 ① 常時起動するプロセスがないため、月次の運用作業が実質ゼロになる。 ② Pages と Workers が同一ドメインで配信されるため CORS 設計が不要。 ③ API が落ちても Pages の静的コンテンツは配信され続けるので、過去の記録は必ず読める（NFR-03）。 ④ 認証を Cloudflare Access に委譲することで、単一ユーザーのためにパスワード管理機構を自作せずに済む。

02データの正本と派生 ─ バージョン履歴の実体

「ソースファイルを重ねて履歴として保存する」という要求を、追記型イベントログ（JSONL）を正本にすることで実現する。 D1 はそこから再生成できる派生物にすぎないため、スキーマを変えても作り直せばよく、全損しても復元できる。

D1 を正本にしない理由。 正本がテキストファイルであれば、Git がそのままバージョン管理装置になり、差分も履歴も無料で手に入る。 スキーマ変更のたびにマイグレーションを書く必要もなく、再生成するだけでよい。 D1 を全損しても vault から完全復元できる（NFR-12 / RPO 1日・RTO 1時間）というのは、 この構成をとった場合の当然の帰結であって、別途バックアップ機構を作る必要がない。

03実行ボタンを押したときの流れ

Workers には CPU 時間の制限があるため、Claude の呼び出しは Queues に逃がして非同期化する。 進捗は Durable Object を経由した SSE でブラウザに返し、成果物は R2 と vault の両方に積層保存する。

コスト上限は Worker 側で必ず止める。 ② の enqueue 前に当日の ai_runs.cost_jpy 合計を確認し、 ai.daily_cost_cap_jpy（既定 300円）を超えていれば BUDGET_BLOCKED として実行を拒否する（FR-F4-06）。 ブラウザ側の制御だけに頼らない。

04技術選定と、その理由

領域採用理由採らなかった選択肢
静的配信Cloudflare Pages無料・グローバルCDN・Workers と同一ドメインで配信できるS3 + CloudFront（IaC と証明書の運用が発生する）
APICloudflare Workers（Hono）コールドスタートがほぼ無く、常時起動コストがゼロLambda + API Gateway（VPC・IAM・デプロイ基盤の運用が必要）
DBD1（SQLite）個人利用の規模に十分。派生物なので作り直せるDynamoDB（集計クエリが書きにくい）／Postgres（常時起動が必要）
正本JSONL（append-only）+ Git履歴管理・差分・バックアップが Git だけで完結するDBのポイントインタイムリカバリ（別途運用が必要）
オブジェクト保存R2エグレス無料。成果物とスナップショットの置き場S3（エグレス課金）
非同期実行Queues + Durable ObjectsWorkers の CPU 制限を回避しつつ、SSE で進捗を返せるSQS + Lambda（構成要素が増える）
排他制御Durable Objects「同時に出撃できるのは1件」を単一の直列化ポイントで保証できるD1 のトランザクション（分散環境で競合しうる）
認証Cloudflare Access（Google IdP）単一ユーザーのために認証機構を自作しないCognito／自前の JWT 発行（過剰）
定期実行Cron Triggers15分毎の同期と日次ロールオーバーに十分EventBridge（別クラウドを持ち込むことになる）
ローカル側Claude Code スキルRunner 定義をクラウドと共有し、同じ処理をローカルでも走らせる専用CLIの自作（保守対象が増える）

06構築の順序

Phase構成作るもの完了条件
Phase 1静的HTML + localStorage のみAP計算・クエスト・出撃/完了・AER手入力で1週間、実際に運用できる
Phase 2+ Workers / D1 / Access / CronAPI化・Googleカレンダー同期・vault と Git 連携カレンダーから自動でクエストが並ぶ
Phase 3+ Queues / Durable Objects / R2AI Runner・成果物保存・日次レポート実行ボタンから Claude が動き、成果物が履歴に残る
Phase 4（追加開発）資産管理・収益管理・スキルツリー・履歴 diffAsset Stock と Gold/AP が可視化される
Phase 1 を localStorage だけで作るのは意図的な判断。 このシステムの成否は技術ではなく「ゲームルールが自分に効くかどうか」で決まる。 効かないルールの上にインフラを積んでも無駄になるため、まず最小コストでルールを検証し、 数値（AP換算・EXP倍率・AERの目標値）を調整してから Cloudflare に載せる。
